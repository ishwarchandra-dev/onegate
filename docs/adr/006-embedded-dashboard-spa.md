# ADR 006: Embedded dashboard — SPA mode with go:embed, one port, precompressed assets

- Status: Accepted
- Date: 2026-10-10
- Phase: 9 (node `p9.embed-decision`)
- Deciders: architect, go-engineer, devops-engineer

## Context

OneGate ships as a **single static binary** — the core product promise
(docs/roadmap.md: "one binary serves UI + API + proxy"). The dashboard
is React Router 7 (framework mode), which by default builds in SSR
mode: `react-router build` emits `build/client` **and** a Node.js
server bundle (`build/server/index.js`, run via `react-router-serve`).

The gateway is Go. Embedding a Node runtime (or shipping one alongside)
would break the no-dependency story, double the distribution surface
(two runtimes to patch, sign, and cross-compile), and complicate the
Docker and npx paths. The constraint set:

1. One binary, one port: `/` (dashboard), `/api/*` (management),
   `/v1/*` + gemini paths (proxy), `/metrics`, `/healthz`.
2. No Node.js at runtime, on any of the 6 release targets.
3. Offline install: the binary must serve the dashboard with zero
   network access (no CDN fonts/scripts).
4. The dashboard is **auth-gated** (first-run setup → login); no
   public, SEO-relevant content exists.

A route audit (this node): zero `loader`/`action` exports across all 8
routes; every view fetches through `/api/*` from the client and renders
behind the session gate. Nothing in the app uses SSR data.

## Options considered

**A. Keep SSR, embed Node** — serve the dashboard with
`react-router-serve` beside the Go binary. Rejected: two runtimes,
breaks the single-binary gate criterion, doubles CVE surface, and the
Docker image stops being scratch-like.

**B. SSR in Go (exec the JS server, or a JS-in-Go runtime)** — no
maintained, boring path for React Router 7 server bundles on Go.
Rejected as exotic (guardrail: stdlib-first, no new exotic deps).

**C. SPA mode (`ssr: false`)** — React Router builds a static
`build/client` (index.html + hashed assets); Go embeds it via
`go:embed` and serves it with a catch-all fallback to `index.html`.
The router boots client-side; all data flows over `/api`. **Chosen.**

**D. Prerender/SSG at build time** — same static output shape as C for
an app with no loaders; adds build complexity for zero content gain.
Subsumed by C.

## Decision

1. **`ssr: false`** in `react-router.config.ts` (with rationale
   comment). The build emits `build/client` only for embedding.
2. **`internal/webfs`** (p9.embed-pipeline) embeds `web/build/client`
   via `go:embed` and serves:
   - exact-match files under `/` with hashed-asset cache headers
     (`immutable` for `/assets/*`),
   - a catch-all fallback to `index.html` (client router owns all
     dashboard paths; `/api`, `/v1`, `/metrics`, `/healthz` are
     registered first and win),
   - **precompressed gzip** served when the client offers it
     (Accept-Encoding) — compression happens once at build time, not
     per request.
3. A **`HydrateFallback`** skeleton replaces the framework's dev
   console fallback for module boot.
4. Dev workflow unchanged (`react-router dev` + Vite proxy to
   `:7420`); the SPA switch only affects production builds.

## Bundle-size evidence (measured, this node)

| Component | Raw | Gzipped |
|---|---:|---:|
| JS (22 chunks, code-split per view) | 572 KB | **175 KB** |
| CSS (Tailwind v4 output) | 60 KB | ~11 KB |
| Inter variable font (6 subsets, woff2, self-hosted) | 224 KB | n/a (already compressed) |
| index.html | 2 KB | 1 KB |
| **Total embedded** | **884 KB** | — |

Binary impact: < 1 MB added to the Go binary — negligible against the
~15 MB baseline. First paint pays 175 KB gzipped JS + the latin font
subset (~30 KB); subsequent loads hit the browser cache with immutable
asset hashes.

## Consequences

- **Positive**: one binary, one port, no Node; dashboard works fully
  offline; identical deployment story on all 6 targets; e2e can run
  against the real embedded serving path instead of `vite preview`.
- **Negative / accepted**: no server-rendered HTML (moot — auth gate;
  no SEO surface), client JS required (the dashboard is an admin tool;
  the *proxy and API* remain fully usable without any JS), slightly
  larger first-load than an SSR shell (175 KB gz).
- The SSR-era `build/server` output remains generated by the toolchain
  but is **not embedded** and not part of any artifact.
- `web/e2e` migrates from `vite preview` to the gateway-served
  dashboard as part of p9.embed-pipeline, keeping the journeys
  meaningful for the shipped artifact.
